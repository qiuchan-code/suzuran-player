# 实时歌词浮层 · 樱花麻薯

在 QQ 音乐（或任何支持系统媒体控件的播放器）播放时，**自动识别当前歌曲并实时跟唱**。

![亮色](shots/demo-light.png) ![暗色](shots/demo-dark.png)

---

## 它怎么工作

```
QQ 音乐播放
    ↓  Windows 系统媒体会话（SMTC）
读取「歌名 / 歌手 / 专辑 / 播放位置」     ← 系统公开接口，不需要登录、不碰音频
    ↓
QQ 音乐公开歌词接口（按歌名+歌手搜 songmid → 取 LRC）
    ↓  解析成带时间戳的行
SSE 推给浮层页面 → 按播放位置高亮当前行
```

**关键点：不碰音频文件、不绕过任何保护。** 只读系统公开的"正在播放"信息 + 公开歌词接口。

## 歌词字体与花字

### 字体：荆南麦圆体

选定的歌词字体是 **荆南麦圆体（KN Maiyuan）**——笔画粗细一致、两端圆润，
清新俏皮但不书法，日常易读。SIL OFL 1.1 开源，可商用、可随包分发。

- 字体文件：`fonts/KNMaiyuan-Regular.ttf`（7.6 MB）
- 只用于**歌词**（当前行 + 下一句）；歌名、时间、按钮仍走 Nunito，数字不会跳。

### 花字：浅粉字面 + 深粉描边

| 项 | 亮色 | 暗色 |
|---|---|---|
| 字面 | `#ffb3c6` 浅粉 | `#ffc2d1` |
| 下一句字面 | `#ffc2d1` | `#ffd2dd` |
| 描边 | `#e8557d` 深粉 | `#c2436a` |
| 描边粗细 | 40px 字 → 2.6px，22px → 1.8px | 同 |

**描边按字号缩放**：固定粗细会让大字描边显得太细、小字显得太粗。

### 一个实测踩出来的坑：描边不能用 `-webkit-text-stroke`

```css
/* ✗ 在 Chrome 里白边/描边出不来，会被字面填充盖住 */
-webkit-text-stroke: 8px #fff;
paint-order: stroke fill;
```

试过的三条路都不行：`paint-order` 救不回来；伪元素绝对定位叠描边会盖住主文字；
绝对定位层上的 `text-stroke` 不生效。

**可用方案是 `text-shadow` 八向环绕**：

```css
text-shadow:
  2.6px 0 0 #e8557d, -2.6px 0 0 #e8557d, 0 2.6px 0 #e8557d, 0 -2.6px 0 #e8557d,
  1.84px 1.84px 0 #e8557d, -1.84px -1.84px 0 #e8557d,
  1.84px -1.84px 0 #e8557d, -1.84px 1.84px 0 #e8557d;
```

任何浏览器都支持，能精确控制粗细，也能叠多层做外圈。

## 快速开始

```powershell
# 1. 启动服务（默认读 QQ 音乐）
node src/server.mjs --port 7788 --app QQMusic

# 2. 打开浮层
#    http://127.0.0.1:7788/
```

在 QQ 音乐里放一首歌，浮层就会自动跟唱。

**参数**：

| 参数 | 说明 |
|---|---|
| `--app <串>` | 会话过滤（如 `QQMusic`）；留空则自动取"正在播放"的会话 |
| `--port <端口>` | 默认 7788 |
| `--poll <毫秒>` | 轮询间隔，默认 1000 |
| `--demo` | 演示模式：假进度 + 真歌词，用来验证跟唱效果 |

**浮层上的快捷键**：`1/2/3` 切装饰档、`d` 切明暗、`h` 隐藏控制条、
`[` / `]` 微调歌词偏移（或点浮层上的 `−1s / +1s`）。

## 实测结论（重要）

### 0. QQ 音乐不上报播放进度（最关键的一条）

实测：QQ 音乐通过 SMTC 只给**元数据**（歌名/歌手/专辑/封面）和**播放状态**，
**播放位置与总时长恒为 `0.0s / 0.0s`**，连采多次也不变：

```
Status   : Playing
Title    : See You Again
Position : 0.0s / 0.0s     ← 永远 0，不更新
```

它的窗口标题只有 `歌名 - 歌手`（没有时间），UI Automation 树里**既没有进度条节点
也没有歌词文本**（162 个节点全查过）。所以**拿不到真实播放位置**。

**解法：合成时钟。** 以"检测到开始播放/切歌"为起点，用墙钟时间推算：

| 事件 | 处理 |
|---|---|
| 切歌 | 归零 |
| 暂停 | 停表 |
| 续播 | 继续 |
| 拖动进度条 | **会漂移** → 用浮层上的 `−1s / +1s` 手动补偿 |

纯顺序播放时误差约 1 秒内；拖了进度条就需要点一下 `+1s` 或 `−1s`。
这是在这条平台限制下能做到的最好效果——除非去挂钩 QQ 音乐内部（脆弱且涉及逆向），
或者做音频指纹识别（重、要联网、要录系统声音）。

**时长**同理：SMTC 不给，用"歌词末行 + 8 秒"估算，所以进度条能走。

### 1. SMTC 能拿到什么

```
App      : QQMusic.exe
Status   : Playing / Paused / Opened
Title    : 一笑倾城若桃花
Artist   : 格雷西西西
Album    : 一笑倾城若桃花
Position : 0.0s / 0.0s     ← QQ 音乐不给
Cover    : True            ← 封面有（还没用上）
```

Windows 11 的 `GlobalSystemMediaTransportControlsSessionManager` 提供这些字段，
**任何接入系统媒体控件的播放器都适用**（网易云、Spotify、浏览器里的网页播放器…）。
换成网易云或 Spotify 时，`Position` 很可能是真实值，那时同步会更准。

### 2. 歌词有"有同步"和"没同步"两种

QQ 音乐的歌词接口对不同的歌返回不同质量：

| 歌 | 返回 |
|---|---|
| 晴天 - 周杰伦 | `[00:02.25]词：周杰伦` → **可同步** |
| 一笑倾城若桃花 - 格雷西西西 | 只有纯文本，无时间戳 → **只能显示** |

所以浮层有三态：

- `synced`：有同步歌词，大字跟唱
- `plain`：只有纯文本，显示"这首歌没有同步歌词"+ 前两句
- `none`：找不到

### 3. 不做跨平台模糊兜底（有意为之）

实测：拿《一笑倾城若桃花》去网易云搜，命中的是汪苏泷的《一笑倾城》——
**不是同一首歌**。跨平台模糊匹配会串歌，比"没有同步歌词"更糟。
所以搜索只接受**完全同名**的结果，宁缺毋滥。

### 4. Windows 上的三个坑（已修）

| 坑 | 现象 | 解法 |
|---|---|---|
| PowerShell 输出编码 | Node 读到的中文是乱码 | 脚本开头设 `[Console]::OutputEncoding = UTF8` |
| CRLF | 正则 `(.*)$` 把 `\r` 吃进值里，解析全空 | 用 `(.*?)\s*\r?$` |
| .ps1 无 BOM | PowerShell 5.1 按 ANSI 读，中文注释把语法拆坏 | .ps1 必须存成 UTF-8 **带 BOM** |

### 5. "QQ 音乐有歌词，浮层说没有" —— 瞬时失败被永久缓存（已修）

现象：某首歌 QQ 音乐明明有双语歌词，浮层却显示"这首歌没有同步歌词"。

排查：同一首歌单独调 `lyricsFor()` 完全正常（`Come Over - Dagny` → 56 行），
说明歌词接口没问题，问题在**服务端运行时的缓存**。

根因：`lyricsFor()` 把**失败结果也永久缓存**了。第一次请求碰上一次网络抖动
（或接口限流、超时），就写入 `{kind:'none'}` 并永久保留，这首歌在本次进程内
再也不会重试——于是"明明有歌词"却一直显示没有。

修复（`src/lyrics.mjs`）：

| 改动 | 说明 |
|---|---|
| 失败不永久缓存 | `none` 只缓存 **30 秒**，之后自动重试 |
| 请求重试 | 搜索/取词都包了 3 次重试（递增退避 400ms / 800ms） |
| 请求超时 | 单次 8 秒超时，避免卡住轮询 |
| 成功永久缓存 | 命中过的结果仍永久保留，不重复请求 |

现在遇到瞬时故障会**自愈**：最多 30 秒后重新尝试，而不是坏一整个会话。

### 6. 切歌延迟 ~800ms（已修：改常驻进程）

现象：切歌后浮层要等一会儿才跟上。

测量：**每启动一次 PowerShell 读一次会话要 ~800ms**（进程启动 + WinRT 初始化）。
之前 Node 每秒调一次脚本，等于每秒烧掉 800ms，切歌感知延迟接近 2 秒。

修复：改成**常驻监视器**（`tools/session-watch.ps1`）——只启动一次进程，
它内部每 250ms 轮询、**只在状态变化时输出一行 JSON**，Node 侧读流即可：

| | 之前 | 现在 |
|---|---|---|
| 读一次状态 | 启动进程，~800ms | 取内存里最近一行，**0.001ms** |
| 轮询间隔 | 1000ms + 800ms 开销 | 250ms（常驻进程内部） |
| 切歌感知 | 接近 2 秒 | 约 0.25 秒 |

顺带一个坑：JSON 输出**不能用 `Write-Output`**，PowerShell 管道会重新编码导致
中文乱码，必须用 `[Console]::Out.WriteLine()` 直接写 stdout。

### 7. 前奏阶段歌词提前滚动（已修：跳过制作信息字幕）

现象：歌曲还在前奏，浮层已经在滚歌词了。

根因：QQ 音乐的 LRC **开头有一串带时间戳的制作信息行**（作词/作曲/编曲/混音…），
播放器把它们当前奏字幕显示，人耳感知的"歌词"从正文才开始。
之前把字幕也当歌词滚了，看起来就像"歌词提前了"。

修复（`src/lyrics.mjs`）：

- `isCreditLine()` 识别中英文制作信息、版权声明、标题行、纯音乐占位文本
- `firstRealLineIndex()` 找出**正文第一行**的时间，作为 `creditUntil` 推给前端
- 前端在 `pos < creditUntil` 期间显示"前奏中 · 歌词马上开始"，不滚字幕

实测效果：

| 歌 | 正文起始 |
|---|---|
| 晴天 - 周杰伦 | 13.5s（前面全是作词/作曲字幕） |
| Come Over - Dagny | 9.6s |
| 晚风告诉我 - 赵薇薇 | 0.8s |

顺带修了**版本匹配**：同名同歌手可能有多个版本（原版 / DJ 版 / 重制版），
歌词时间轴不同。现在用搜索接口返回的 `interval`（时长）在候选里挑最接近的，
时长差超过 3 秒就不认，避免匹配到别的版本。

### 8. 纯音乐被当成歌词

歌词是"此歌曲为没有填词的纯音乐，请您欣赏"这类占位文本时，
现在识别为**没有歌词**，不会把这句当歌词显示。

## 结构

```
overlay/
  src/
    track-reader.mjs    读系统媒体会话（调 tools/now-playing.ps1）
    lyrics.mjs          搜歌 + 取 LRC + 解析 + 三态分类
    server.mjs          HTTP + SSE，轮询会话、切歌取词
    live.mjs            浏览器端数据层（被播放器界面内联使用）
    live-inline.mjs     把 live.mjs 内联进页面的包装
  tools/
    now-playing.ps1     WinRT 读 SMTC（-List / 默认读一次 / -Watch 轮询）
    session-watch.ps1   常驻监视器（只启一次进程，省开销）
    probe-apis.mjs      歌词/搜索接口可用性排查
    probe-ratelimit.mjs 限流行为排查
```

> **定位说明**
>
> 这个服务最初配套一个"歌词浮层"页面（`overlay.html`）。
> 后来浮层演变成了完整的播放器界面（`player-ui.html`），
> 浮层页与它的构建脚本、截图脚本、一次性数据转储脚本都已移除。
>
> 现在 `overlay/` 的定位是**播放器的歌词数据服务**：
> `server.mjs` 由 `src/launcher.ps1` 拉起，`live.mjs` 被
> `src/build-player-ui.mjs` 内联进界面。

## 已知限制

- **位置精度**：QQ 音乐不给播放位置，用合成时钟推算。顺序播放误差约 1 秒内；
  **拖动进度条后会漂移**，需要点 `+1s / −1s` 手动补偿（或调 `/api/seek?to=秒数`）。
- **时长**：SMTC 不给，用歌词末行 + 8 秒估算，所以进度条是近似的。
- **暂停/续播**：`Status` 能跟上，停表/续表正确。
- **没有歌词的歌**：显示"没有同步歌词"，不会瞎猜。
- **浮层是网页**，不是真·置顶窗口。要它盖在 QQ 音乐上面，可以用浏览器窗口置顶工具
  （如 PowerToys 的 Always on Top），或后面做成 Electron/Tauri 小窗。
- 换用网易云 / Spotify 时，`Position` 通常是真实值，同步会明显更准。
