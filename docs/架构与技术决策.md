# 架构与技术决策

这份文档记录**为什么这么写**。很多地方看着绕，都是踩过坑才改成现在这样的。

---

## 整体数据流

```
QQ 音乐（进程）
     │
     │ Windows SMTC（系统媒体传输控件）
     ▼
session-watch.ps1  ← 常驻 PowerShell 进程，250ms 轮询一次会话
     │               只在内容变化时往 stdout 吐一行 JSON
     │ stdout（管道会重新编码导致中文乱码，所以用 [Console]::Out.WriteLine）
     ▼
track-reader.mjs   ← 读子进程输出流，解析 JSON，放在内存里
     │               read() 是同步的，耗时 ~0.001ms
     ▼
server.mjs         ← 250ms 轮询 reader，发现变化就：
     │                ① 立刻广播曲目信息（不等歌词！）
     │                ② 后台异步取歌词，取到再广播一次
     │
     │ HTTP + SSE
     ▼
serve.mjs（反向代理 /api/* → 7788）  ← 让界面和接口同源
     │
     ▼
player-ui.html     ← live.mjs 拉快照 + 订阅 SSE
                    每帧补间推算播放位置
```

---

## 几个关键决策

### 1. 为什么用常驻 PowerShell 进程读会话

每次启动 PowerShell 读一次 SMTC 要 **~800ms**。如果 Node 每秒 spawn 一次，
光是进程启动就烧掉 800ms，切歌感知延迟接近 2 秒。

改成"启动一个常驻进程，内部高频轮询，只在变化时输出一行"，
Node 侧只需读流，**切歌延迟降到 250ms**（轮询间隔本身）。

### 2. 为什么曲目信息和歌词要解耦

早期写法：

```js
broadcast()                              // 推曲目
const lyrics = await lyricsFor(track)    // ← 这里 await 卡住整轮循环
```

接口慢的时候（旧接口限流每次要等 5 秒），`tick()` 被堵住，
**期间任何曲目变化都读不到**——表现就是"切歌后曲名半天不更新"。

现在：

```js
broadcast()                          // 曲目立刻推
lyricsFor(track).then(...)           // 歌词后台取，取到再补推
```

### 3. 为什么播放位置是"推算"的

QQ 音乐**不通过 SMTC 上报播放位置和时长**（`Position` / `EndTime` 恒为 0）。
也试过 UIAutomation 读进度条节点，读不到。

所以位置靠：

```
位置 = 收到快照时的位置 + (当前时刻 - 收到快照的时刻) × 播放中
```

用**单调时钟**而不是"每秒加一"，因为浏览器标签页切到后台时定时器会被节流，
"每秒加一"会越走越慢。

**后果**：拖动 QQ 音乐的进度条后，界面位置会偏。用设置里的"歌词对齐"补偿。

### 4. 为什么封面要绕一圈从搜索接口拿

按顺序试过：

| 方案 | 结果 |
|---|---|
| SMTC 的 `Thumbnail.OpenReadAsync()` | ✗ 对 QQ 音乐返回**空流**（`size=0`） |
| `IRandomAccessStreamWithContentType.Dispose()` | ✗ PowerShell 拿到的是 `__ComObject`，没这方法，抛异常还会把整个读取拖失败 |
| `BitmapDecoder` 重编码 | ✗ 类型要显式预加载，且 `CreateAsync` 重载对不上 |
| **搜索接口的 `album.mid` 拼 URL** | ✓ **稳定，500×500 JPEG** |

最终：

```
https://y.qq.com/music/photo_new/T002R500x500M000{album.mid}.jpg
```

### 5. 歌词接口的限流与匹配

**限流的坑**：接口被限流时**不返 HTTP 错误**，而是返

```json
{ "req": { "code": 2001, "data": null } }
```

HTTP 200、body 正常、就是没数据。早期的代码把它当成"这首歌搜不到"，
于是**永久缓存 + 不重试**——表现就是"经常显示不出歌词"，而且不会自愈。

现在：
- 识别 `code != 0`，抛特定错误走长退避
- 加**请求闸门**：所有搜索请求排队，两次之间最少隔 3 秒
  （实测 1.2 秒间隔下第 10 次左右翻车，3 秒间隔下 12 连击全过）
- 限流后**整体冷却 60 秒**，期间不试探（越试越糟）
- **失败自动补取**：每 25 秒重试一次，冷却结束自动补上

**匹配策略**（从严到宽）：

1. 歌名完全相同 + 歌手能对上
2. 歌名完全相同（歌手对不上）
3. 主标题（去版本号）+ 歌手能对上
4. 主标题相同（歌手对不上）

歌手完全对不上**且标题也不同**就放弃——宁可没歌词，也不串歌。

"主标题"是剥掉 `(Phonk)` / `(Live)` / `-Remix` 这类版本标记后的名字。
播放器的曲名常带版本号，而曲库存的是不带版本号的名字。

### 6. 歌词首段字幕要跳过

LRC 开头常有一串带时间戳的**制作信息**：

```
[00:00.00]晴天 - 周杰伦 (Jay Chou)
[00:02.25]词：周杰伦
[00:04.50]曲：周杰伦
```

QQ 音乐在前奏期间把它当字幕显示，但网页这边会变成"歌词提前滚动"。
所以 `isCreditLine()` 识别这类行，算出正文开始的时刻 `creditUntil`，
在此之前显示"前奏中 · 歌词马上开始"。

实测：晴天 13.5s、Come Over 9.6s、晚风告诉我 0.8s。

### 7. 为什么文字描边用 text-shadow 而不是 -webkit-text-stroke

```css
/* ✗ 在 Chrome 里描边出不来，会被字面填充盖住 */
-webkit-text-stroke: 8px #fff;
paint-order: stroke fill;
```

试过三条路都不行：`paint-order` 救不回来；伪元素绝对定位叠描边会盖住主文字；
**绝对定位层上的 `text-stroke` 不生效**。

可用方案是 `text-shadow` **八向环绕**：

```js
function ringShadow(color, px) {
  const k = px * 0.7071   // 对角方向，保证是圆形环绕而不是方框
  return [[px,0],[-px,0],[0,px],[0,-px],[k,k],[-k,-k],[k,-k],[-k,k]]
    .map(([x, y]) => `${x.toFixed(2)}px ${y.toFixed(2)}px 0 ${color}`).join(', ')
}
```

任何浏览器都支持，能精确控制粗细，也能叠多层做外圈（大钟就用了两层）。

### 8. 为什么把 ES module 内联进页面

`player-ui.html` 是单个自包含文件，但 `timer.mjs` / `live.mjs` 是 ES module。
页面里的内联 `<script>` 没有模块上下文，跑不了 `import`。

所以构建时：

```js
raw.replace(/^export const /gm, 'const ')
   .replace(/^export function /gm, 'function ')
```

剥掉 `export` 关键字，再包一层作用域执行。**逻辑只有一份**，
Node 里能跑单元测试，页面里也能跑。

### 9. 为什么"构建时算好"而不是"页面里跑函数"

内联脚本没有模块上下文，页面里不能调用构建脚本里的函数。
所以所有需要计算的样式串（描边、发光）都在**构建时算成字符串**，
再 `JSON.stringify` 塞进页面，页面只负责读。

### 10. 尺寸与字号的适配

`--w`（右栏实际宽度）由 `ResizeObserver` 实时写进 `:root`，
字号和封面尺寸都从它推导。窗口一改大小，整块版面等比缩放。

**挂在 `:root` 而不是 `.right`** 是有原因的：右下角表情按钮在 `body` 下，
不在 `.right` 里，挂 `.right` 的话它取不到 `--w`，宽度会算成 0。

歌名过长时用**二分查找**缩字号：区间 70→35 逐像素降要试 30 多次，
每次都要读 `scrollWidth`（**强制重排**），而这段代码跑在每帧循环里。
二分只要 6 次。

### 11. 昼夜更替怎么做的

原片（铃兰雪霁·昼夜更替）的亮度实测：

| 时间 | YAVG | 判定 |
|---|---|---|
| 0–20s | ≈169 | 白天 |
| 24–28s | ≈107 | 夜晚（夜色 + 铃兰发光） |
| 32–44s | ≈135 | 黄昏 |
| 48s+ | ≈107 | 夜 |

所以切两段分别导出成循环短片（白天 3.7MB / 夜晚 5.0MB），
叠在一起按主题交叉淡入淡出，过渡 **1.2 秒**——不是硬切。

### 12. 表情随节奏抖动

用户给了两张 GIF：睁眼（舒展）、闭眼（鼓劲）。

**不用 GIF 重播**——从头播会闪一下，节奏也对不齐。
改成两张叠加，靠**透明度**切换：

- 压缩量由正弦驱动（约 1.1 秒一循环，像 55 BPM 点头）
- `scaleY` 从 1 到 0.5（正好半高），`transform-origin: 50% 100%`
  在底部，压下去像"蹲一下"
- 压缩超阈值才切闭眼，**避免在边界反复抖**

### 13. 反代 /api 是为了同源

界面和歌词接口本来是**两个端口**（7790 / 7788），跨域。
`serve.mjs` 把 `/api/*` 转发到 7788，这样界面和接口**同源**，
一个地址就能用，不用处理 CORS。

SSE 也必须**流式转发**（`up.pipe(res)`），不能缓冲，否则歌词不实时。

node src\timer.test.mjs    # 注：测试文件在 overlay 那边，见下
